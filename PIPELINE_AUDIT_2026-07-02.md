# Receipt Pipeline Audit — 2026-07-02

Scope: capture → OCR → parse → client/server handoff → matching → price integrity → swipe/learning → documentation. 
Method: 7 parallel code auditors (every finding requires quoted code evidence) → adversarial verification of each finding (2 independent verifiers for high severity) → main-agent re-verification of rate-limited items. 65 findings raised, 1 refuted, 64 retained.

Verification legend: **CONFIRMED** = verified against code (by verifier agents or main-agent re-read); **PLAUSIBLE** = auditor quoted evidence but independent verification was rate-limited — treat as probably-real, re-check before large refactors.

## Dimension summaries

### capture-ocr (8/8 findings survived)
The capture+OCR core is in good shape: tile y-offsets, the iOS-downscale/Android-upscale invFactor remap, multi-page yOffset accumulation and the seam dedupe-before-remap ordering are all internally consistent, well-commented, and the interactive merge pass matches receiptOcrPipeline's byte-for-byte. The real weaknesses are cross-path divergence rather than core math: the iosOcr row-fragment flag is dropped on the headless-queue and account-recovery parse sites (wrong iOS Maxima/Lidl parses, recovery-match drift), and region rehydration re-parses IKI from raw unmerged, non-enhanced lines yet authoritatively overwrites stored total/date/time/receiptNo — a reopen-time corruption vector. Secondary risks are edge-case geometry (no width cap + a one-sided frameScale clamp on >4096px-wide Android inputs, exact-text tile-seam dedupe, Image.getSize-based portrait checks in three drifted copies) and a multi-page hole in the flag-enabled product re-OCR splice that can delete page-2 products when no total parsed.

### parsers-consistency (8/8 findings survived)
The five parsers' output contract is in good shape at its core: after each chain's normalization pass, 'price' is consistently the PER-UNIT price (per kg / per item), promoPrice the per-unit discounted price, and all five return empty/partial results rather than throwing — the price×quantity convention is uniform and the server (receiptSaveService.ts:335) can safely treat line.price as the unit price. The real defects live at the edges: Lidl's optional-ppu unit-line regex can emit quantity>1 with price still the line total (reference-price poisoning, the one genuine contract break found), Norfa mislabels exact-integer-kg weighed rows as 'vnt', and Maxima's parsedAmount/parsedUnit contract fields are dead (never populated, with the app's Maxima branch alone lacking the name-derived fallback). Mechanically, the root-shared vs app-copy sync has no divergence guard on the OTA and local-test paths, and both repos' CI checks out the shared repo unpinned to a branch. Chain detection ordering (Rimi→Maxima→Norfa→Lidl→IKI, VAT fallback last) is mirrored between the gate and the dispatch and I could not construct a realistic cross-claim; region shapes are handled uniformly through bandQuad with safe fallbacks, though the documented xMid 8-point shape is now emitted by nobody.

### client-server-handoff (10/10 findings survived)
The handoff protocol (POST → parallel masked upload → debounced PUT) is thoughtfully guarded on the client (receiptId gating, draft resume with 24h expiry, fail-closed mask), and the core save is one transaction with points/propagation correctly deferred past commit. The critical weakness is the ReceiptItem migration's afterlife: the 'non-fatal' dual-write catch plus Price.receiptItemId ON DELETE CASCADE means every autosave PUT silently deletes and re-adjudicates the receipt's items and prices, so a single swallowed INSERT failure, a shifted clearance baseline, or a stale-state rewrite can permanently destroy data the docs promise is append-only. A second theme is one-sided mutations losing to the full-blob rewrite: user reject-match, Card-B demotions, and issue-report unverification are all revertible by the very next debounced save because the resolver has no rejection memory and the client/blob state is never synced. Duplicate handling is mostly clean (nothing written before the same-user check), but raw-vs-normalized receiptNo comparison can mislabel same-user duplicates as cross-account, and mutating endpoints lack ownership checks.

### matching (9/10 findings survived)
The matching engine's core lanes (token/char/subset/heal, anchor gate, weighable gate) are internally coherent and well-guarded, and the resolver's no-mint decision logic itself never links a wrong-chain SP — but the save-flow glue leaks: an unmatched line keeps its stale (possibly cross-chain) storeProductId and gets persisted into ReceiptItem.matchedSpId with a mislabeled 'skipped_unpriced' source, the two highest-impact findings. Round-2 is solid except for weighable lines missing pricePerUnit, where it anchors on the fractional line total and can falsely reject or repick a correct match. Post-max per-candidate penalties (numberMismatch, unit-family) interact badly with the alias lane and with each other, quietly demoting exact learned aliases and same-size-different-unit products below auto-apply. Config hygiene lags the code: four knobs are dead, tokenMatchThreshold/significantMinLen are split-brain, several @refs are stale, and the per-line full-catalog refetch + renormalization is the dominant hoistable cost (~13k normalizations and one heavy JOIN per line).

### price-integrity (10/10 findings survived)
Price-writing itself is sound on the unit-price question — parsers emit per-unit (and per-kg) prices with the weighed price=0 poisoning guard, and the save loop's skip conditions (price<=0, implausible, clearance, duplicate, mixed-deal) are coherent. The two high-severity problems are elsewhere: getUserStats was never migrated off the now-empty blob products[] (profile stats/savings silently exclude every post-cutover receipt), and the swipe undo path blindly inverts priceVerified without knowing which vote it is undoing (a 'similar'+undo can mark an unverified OCR price as verified, feeding the baseline/clearance machinery). The fallback propagation layer has a cluster of medium integrity gaps: no recency guard on the update path (old receipts regress newer fallback data), promo rows fan out with promoEnd NULL and read as eternally active promos, a rejected match's propagated copies are never reverted, and the deprecated wrapper's receiptId??0 breaks the manual-price endpoint. The midnight-padded receipt date plus the ON DUPLICATE KEY 'last write wins' in createPrice lets one receipt hijack another's Price row, which then confuses vote flips and DEV deletion. Deletion itself cleans fallback rows correctly (FK RESTRICT prevents dangling rows), leaving only a narrow race with the fire-and-forget propagation.

### swipe-learning (9/9 findings survived)
The swipe-learning loop's core weakness is that StoreProductMatchVote rows don't record whether they were ever aggregated: burst votes write rows (receipt path) or nothing at all (direct/slot2 paths), and every reversal/edit/reset path then guesses wrong — undo and editVote can drive StoreProductMatch counts negative (no clamp), the reset recompute only repairs pairs it happens to touch, and burst direct votes bypass both the no-repeat rule and the rate limit while still earning points. A second theme is cross-service semantic drift: 'similar' maps to opposite personal-equivalence verdicts in castSwipeVote vs castDirectSpPairVote/slot2, and the price-flip undo helper toggles priceVerified blindly against its own documented contract. The alias state machine and queue no-repeat logic are otherwise solid (shared deriveAliasStatus, consistent recompute), and the mandatory-session issues are cosmetic.

### docs-drift (10/10 findings survived)
Documentation is unusually rich but the recent no-mint cutover (RECEIPT_ITEM_MIGRATION P3) and matcher-lane growth outran several docs: SWIPE_QUEUE_REDESIGN.md, RECOGNITION_PIPELINE.md stage 6, and receiptLineResolver's own header all still describe orphan/SP minting that no longer exists, and RECEIPT_ITEM_MIGRATION's '✅ COMPLETE' claim masks that statsService.getUserStats — on the doc's own must-migrate list — still reads the now-empty blob products[], a likely live profile-stats regression. recognitionConfig.ts overstates itself: its ocr/parse sections are unwired mirrors of literals still inlined in mlkitOcr/parsers, and most @ref line numbers have rotted. RECEIPT_VOCABULARY.md and WORKFLOW.md check out cleanly against code.

# Authorization sweep — the rest of the API + souply-web (extends the receipt IDOR fix)

The receipt authz fix closed one of ~5 exposed surfaces. This sweep closed the rest. Audit: every user-owned route across all routers + souply-web mapped to its correct guard, risky classifications (cross-user forks, share-token claims) adversarially verified so nothing over-guards a legit flow. Shipped to dev; api 923 tests / app 550 / web 19 / all tsc-clean.

## New auth primitives
- `middleware/sessionAuth.ts`: `requireUser` gained a **non-prod-only** `X-User-Id` dev-header shim (souply-web's dev/staging build authenticates that way; prod strictly requires a token/cookie — same NODE_ENV convention as the dev receipt-purge). `requireSelfUserParam` now takes a param-name (userRoutes use `:id`).
- `middleware/resourceAuth.ts`: `requireBasketOwner` / `requireBasketItemOwner` / `requireBasketTemplateOwner` (strict owner), and `requireListMember` / `requireListMemberFromBody` / `requireListItemMember` (collaborative) / `requireListOwner` (strict, destructive delete only). Model lookups: `getBasketOwnerId`, `getBasketItemOwnerId`, `getBasketTemplateOwnerId`.

## Per-router outcome
- **userRoutes** — SELF-ONLY (`requireUser` + `requireSelfUserParam('id')`) on all `/users/:id[/**]`, incl. the headline **unauthenticated `DELETE /users/:id` account deletion**, profile/stats/equivalences/votes. `POST /users` (token bootstrap) + `POST /users/recover` (proof-of-knowledge, rate-limited) stay open by design.
- **baskets / basket-items** — STRICT owner on every `:id` route (no share/public flow); `copy` forks an owner-only source into a new basket owned by the caller; create/`user/:userId` = requireUser/self-param. Identity from token in `addBasket`/`copyBasket`.
- **shopping-lists / list-items** — MEMBERSHIP model: any `ShoppingListMember` for reads/edits/items/duplicate/share/link-receipt; STRICT creator only for `DELETE`; **share-token status/claim = `requireUser` only (token possession IS the authz — a member check would break claiming)**. `link-receipt` additionally requires the caller to own the receipt; `addShoppingList` checks basket ownership when created from a basket.
- **orphan votes / template-cover upload** — identity from the token (closes the spoofable-userId Sybil + cross-user cover upload).

## souply-web
- **Live prod IDOR fixed (was HIGH):** `basketTemplateController.callerId()` fell back to the raw `X-User-Id` header in ALL environments → an unauthenticated attacker could act as any user on every template route. Now derives identity from `req.authUserId` (token/cookie; the header is only honored by the non-prod shim), and the template routes are `requireUser`-guarded.
- **Prod web is transparent:** the SPA authenticates with the httpOnly `souply_session` cookie via `credentials:'include'`, which `getSessionToken` reads — so switching controllers to `req.authUserId` needs **no web-side change**. Its `X-User-Id` is already dead-code-eliminated from prod builds and aligns with the non-prod server shim for dev. No souply-web SPA code change required; the fix was server-side.
- Confirmed clean: token lives only in the httpOnly cookie (no XSS theft), the web `server/` BFF is read-only over public `/api/t/:slug` (no IDOR), CSRF mitigated by SameSite=Lax + JSON-preflight + strict CORS allowlist (accepted).

## Deploy ordering
API enforcement is breaking for un-updated clients. Mobile: ship the token-sending app build together with the API (or version-gate). Web: **prod web already sends the cookie → no break**; dev/staging web relies on the non-prod `X-User-Id` shim. `SESSION_JWT_SECRET` required in every env (OAuth already needs it).
